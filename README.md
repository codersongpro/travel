# 여행 코스 플래너

날짜와 총예산, 원하는 코스 테마를 고르면 **식당 · 액티비티 · 숙소**를 찾아
날짜별 동선으로 짜 주는 웹앱입니다.

- **코스 테마 14종** — 교육·학습, 미식, 역사·유적, 자연·힐링, 문화·예술, 액티비티,
  쇼핑, 야경, 휴양, 포토스팟, 가족, 로컬 체험, 종교, 스포츠
- **테마는 하루 안에서 섞입니다.** `오전 박물관 → 점심 맛집 → 오후 공원 → 저녁 맛집`처럼
  한 동선에 여러 테마가 엮이며, 테마별로 날짜를 통째로 나누지 않습니다.
- **식당은 평점과 리뷰 수를 함께 반영**해 고릅니다 (베이지안 가중 평점).
- **실제 이동시간을 계산**해 무리한 동선을 만들지 않습니다.
- 지도 · 예산 배분 · 공유 링크 · PDF 내보내기

## 빠른 시작

```bash
npm install
npm run dev      # http://localhost:3000
```

**API 키가 하나도 없어도 전부 동작합니다.** 키가 없는 영역은 샘플 데이터로 채워지고,
화면 상단에 어떤 부분이 샘플인지 표시됩니다.

## API 키 설정

`.env.example`을 `.env.local`로 복사한 뒤 필요한 값을 채우세요.
채운 만큼만 실제 데이터로 바뀝니다.

```bash
cp .env.example .env.local
```

| 키 | 발급처 | 없으면 |
|---|---|---|
| `GEMINI_API_KEY` | [AI Studio](https://aistudio.google.com/apikey) | 규칙 기반 일정으로 대체 |
| `GOOGLE_MAPS_API_KEY` | Google Cloud Console | 샘플 장소 + 직선거리 추정 |
| `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` | Google Cloud Console | 지도 대신 좌표 목록 |
| `AMADEUS_CLIENT_ID` / `_SECRET` | [Amadeus](https://developers.amadeus.com) | 등급별 추정 요금 |

### ⚠️ Gemini 키로는 장소 검색을 할 수 없습니다

AI Studio에서 발급한 `GEMINI_API_KEY`는 Generative Language API 전용이라
Places API·Routes API·Maps JS API에는 쓸 수 없습니다. 장소 검색용 키는
Google Cloud Console에서 따로 발급해야 하며, 다음 API를 **모두 활성화**해야 합니다.

- **Places API (New)** — 식당·액티비티 검색, 평점·리뷰 수
- **Routes API** — 장소 간 실제 이동시간
- **Maps JavaScript API** — 지도 렌더링 (`NEXT_PUBLIC_` 키, HTTP 리퍼러 제한 필수)

### 왜 숙소만 Amadeus인가

Google은 개발자용 공개 호텔 API를 제공하지 않습니다. Google Hotels 데이터는
승인된 호텔·OTA만 쓸 수 있는 [Travel Partner API](https://developers.google.com/hotels)로만
접근되며, 셀프서비스로 쓸 수 있는 Places API는 호텔의 이름·평점·가격대는 주지만
**실제 객실 요금은 주지 않습니다.** 그래서 실제 1박 요금은 Amadeus에서 가져옵니다.

## 동작 방식

```
입력 → 도시 좌표 → 테마별 후보 검색 (병렬)
                  ├─ Places API: 액티비티 + 식당 (평점·리뷰 수 포함)
                  └─ Amadeus:    숙소 + 실제 1박 요금
     → 식당 가중 평점 랭킹
     → 좌표 클러스터링 (하루 = 한 권역) → Routes API 이동시간 행렬
     → 예산 카테고리 배분
     → Gemini 일정 생성 (후보·이동시간·예산을 전부 데이터로 전달)
     → 서버 검증 및 교정
     → 결과
```

### 식당 랭킹 — 평점만 쓰지 않는 이유

평점만으로 정렬하면 *리뷰 3개에 5.0점*인 신생 가게가 *리뷰 4,000개에 4.5점*인
검증된 맛집을 이겨 버립니다. 그래서 리뷰 수를 신뢰도로 삼는 베이지안 가중 평점
(IMDb 가중 평점과 같은 공식)을 씁니다.

```
score = (v / (v + m)) × R + (m / (v + m)) × C
R = 평점,  v = 리뷰 수,  m = 신뢰 기준(100),  C = 후보군 평균 평점
```

리뷰가 적으면 점수가 평균 쪽으로 끌려 내려가고, 많으면 자기 평점을 온전히 갖습니다.
리뷰 20개 미만은 표본 부족으로 제외합니다.

### 이동거리 — 직선거리를 쓰지 않는 이유

강·산·일방통행 때문에 직선거리는 실제 이동시간과 크게 어긋납니다.

1. 후보를 좌표로 클러스터링해 **하루치를 한 권역**으로 묶습니다 (무료, 호출 전)
2. 권역 안에서만 **Routes API로 실제 이동시간 행렬**을 구합니다
   (N×N 과금이라 권역 단위로 잘라 호출량을 제한)
3. Routes API를 못 쓰면 `Haversine × 우회계수`로 폴백합니다

검색 반경도 이동 수단에 맞춰 달라집니다 — 도보 1.5km, 대중교통 12km, 차량 25km.
도보 여행에 15km 반경으로 후보를 모으면 하나도 이어 붙일 수 없기 때문입니다.

### 서버가 모델 응답을 검증합니다

Gemini 응답을 그대로 쓰지 않고 서버에서 다시 강제합니다.

- 후보 목록에 없는 `placeId`는 제거 (환각 방지)
- 이동시간 초과 구간은 **같은 테마의 더 가까운 곳으로 교체**
- 고르지 않은 테마의 장소 제거
- 식당 중복 제거, 전체 일정 장소 중복 제거
- 예산 초과 시 같은 테마의 더 합리적인 곳으로 교체

#### 제약을 못 지킬 때는 숨기지 않고 알립니다

후보가 부족하면 모든 제약을 동시에 만족할 수 없습니다. 그럴 때 앱은
일정을 비우는 대신 **차선을 택하고 그 사실을 화면에 표시**합니다.

- 가까운 식당이 없으면 → 저녁을 없애지 않고 가장 가까운 곳을 넣되
  `이동이 다소 깁니다`로 표시
- 예산 안에 활동을 다 못 넣으면 → 하루를 비우지 않고 예산 패널에 초과분과
  줄이는 방법을 안내
